## 2026-10-05 T3 admin users: deactivation
- profiles.is_active (boolean not null default true, migration 0005). Deactivation is two layers: the flag and an auth ban (updateUserById ban_duration 876000h, "none" to reactivate). Verified locally: a banned user's OTP verify returns "User is banned"; unbanning restores sign in.
- dlv_role, dlv_is_staff, dlv_is_admin, dlv_customer_id and dlv_carrier_id all filter on is_active. An inactive user has a NULL role, so every policy, set_load_status, set_load_eta, the approve/reject functions and the storage helper dlv_can_access_doc (it returns false on a NULL role) deny them with no per-policy edits.
- profiles_select read the table directly for the "self" branch, so it now requires is_active too. An inactive user whose JWT is still valid (up to the token lifetime) therefore gets no profile, and the app sends them to /login.
- The profiles scope CHECK is unchanged: is_active is orthogonal to role, customer_id and carrier_id. Authenticated still has no INSERT, UPDATE or DELETE on profiles (service role only); the new column adds no grant. Tested: authenticated cannot update is_active.
- Server actions (deactivateUser, reactivateUser, inviteUser, removeUser) call requireAdmin first. Deactivate refuses self and the last active staff_admin; remove also refuses the last active staff_admin. If the ban call fails after the flag was set, the flag is rolled back.
- inviteUser validates scope against the database (customer exists, carrier exists and is active), lowercases the email, and returns one generic message for a duplicate email. Auth user is created with email_confirm true; it is deleted if the profile insert fails.
- Follow-up for other owners: src/app/team/actions.ts (owner adds drivers) and notify.ts files read profiles through the service role and do not yet filter is_active, so an inactive user could still be emailed or listed there.

## 2026-10-05 C3 failure UX
- Status writes are guarded twice. Client: a ref lock plus the busy state disable every mutation button on the first tap. Server: advanceLoad takes expectedFrom (the status the client acted on) and, if the load has moved on, writes nothing and answers "already updated" (code stale); the client refreshes. set_load_status stays the only status writer and still enforces one step forward, which settles a race between the read and the write.
- Watchdog: every browser side mutation (status, ETA, POD, booking submit, cancel) is wrapped in withTimeout (default 25000 ms, NEXT_PUBLIC_ACTION_TIMEOUT_MS overrides, 4000 for the e2e server). On timeout the busy state clears and the message says it is taking too long. The request cannot be cancelled, so a late result is ignored and a timed out POD attempt stops before the next step.
- POD upload keeps one storage path per chosen photo and reuses it on retry ("already exists" counts as uploaded). Carriers cannot delete storage objects, so a fresh path per attempt would orphan files. The saved POD is reused (podDone) so a retry never adds a second POD row.
- Session expiry: the proxy redirects a page visit to /login?next=<path and query>. A server action call without a session gets 401 text/plain "SESSION_EXPIRED" (a redirect would break the action response); the client then goes to /login?next=<current page>. safeNext accepts only a single slash path (no //, backslash, control characters, /login or /auth/*, also checked after decoding). The login form and /auth/callback both apply it.
- Known gap: createLoad has no idempotency key. If a booking request lands after the watchdog fired and the user submits again, two requested loads can exist. Closing it needs a client request id column (migration), left for an owner decision.

## 2026-10-05 C4b documents bucket security (migration 0007)
- Finding: before 0007, dlv_can_access_doc only split the name on '/', and the load_documents CHECK was "storage_path like load_id/kind/%". Names with '..' segments, empty segments, '%2e%2e', trailing space or newline, extra segments and non-uuid file names were accepted by both (measured: 16 of 22 malformed shapes accepted by the function for staff, and the same names inserted into load_documents). No real file was reachable through them, but a name is what the RLS and the app trust.
- Fix: a document path must match exactly {load uuid}/(bol|pod)/{file uuid}.{2 to 5 char lower case alphanumeric extension}, lower case, anchored at both ends. dlv_can_access_doc checks the shape first, before any role or load lookup. The load_documents CHECK uses the same regex and also requires the folder and kind to equal the row's load_id and kind. Both apps already build paths this way (BOL: random uuid plus the lower-cased extension from pdf, png, jpg, jpeg, webp, heic; POD: random uuid plus .jpg), so real uploads stay valid.
- Bucket: private (unchanged), file_size_limit 15 MB, allowed_mime_types pdf, png, jpeg, webp, heic, plus image/heif (some browsers label .heic that way). Matches the UI limits; the server now enforces them too.
- Anon: no storage.objects policy for anon or public touches the bucket (both documents policies are to authenticated); anon has no EXECUTE on dlv_can_access_doc (asserted by grant, never called as anon).
- Tests: supabase/tests/rls.sql section 10 (read isolation across carriers and customers, upload rights by role and load status, 24 malformed path shapes on both tables for a staff user and a carrier, bucket settings). The older fixtures that used the file name x.jpg or x.pdf now use uuid names, since those names are no longer valid.
- Apply: 0007 must go in docs/APPLY-PACK.md. It is idempotent (create or replace, drop constraint if exists, update by bucket id) and needs the load_documents table to hold only conforming rows (production is empty).

## DLV-027 Admin delete of loads (defaults, owner may change)
- Only an active staff_admin can delete a load forever (chris@dlvlogistics.com). Enforced three times: the card is not rendered for anyone else, the server action calls requireAdmin first, and the database function delete_load_forever checks dlv_is_admin() itself. A csr, a customer, a carrier and an inactive admin are refused at the database.
- The function is the ONLY path. No DELETE privilege on loads for any client role and no DELETE policy were added (not needed: the function is SECURITY DEFINER and runs as the table owner). Catalog check before writing it: exactly two foreign keys reference loads (load_events, load_documents), both ON DELETE CASCADE, and no DELETE trigger exists, so nothing else can block a delete and no other table needed handling.
- Typed confirmation: the ITS number when set, otherwise the request ref (the request ref is refused while an ITS number is set, so the admin reads the number off the screen). Compared after trimming spaces, case sensitive. The modal compares exactly (no trimming) so the button never enables on a near miss.
- A minimal audit record stays: table load_deletions (request ref, ITS number, last status, deleted_by, deleted_at, orphan_paths). No foreign keys, so deleting a user later never blocks. It holds no customer, route, contact or document data. Readable by an active staff_admin only; written only by the two functions. Default is to keep it; the owner may ask for none (QUESTIONS.md).
- Files: the database cannot remove storage objects, so delete_load_forever returns the document paths and the server action removes them with the service role client, only paths of the strict shape that belong to that load. If removal fails the load is already deleted: the paths go to load_deletions.orphan_paths (record_load_deletion_orphans, admin only, refuses paths of another load and a load that still exists) and the banner says so. Nothing fails silently and nothing is left half deleted. Known limit: a file uploaded to storage whose row was never inserted (an upload that failed between the two steps) is not in the list and stays as an unreferenced object.
- Concurrency: the function locks the load row, so a document insert racing with a delete waits and then fails on its foreign key. No document row can survive its load.
- Double submit: the modal locks synchronously (a ref, not only a disabled button), and a repeated call finds no load ("This load no longer exists"), so a delete happens once.
- The deleted banner takes the number from the URL, so it is validated (letters, digits and dashes only, at most 40) before it is shown. It states only what the admin just did.
- Realtime: loads and load_events deletes reach the open lists through the existing LiveRefresh (and its 15 second poll).
- Apply: docs/APPLY-PACK-5.md (0014), a separate owner supervised session; migration first, then the app. Deploying the app first is also safe (the button would answer "could not be deleted" until the apply).


## DLV-028 Lane references: which old ITS load to copy (defaults, owner may change)
- Staff only, three layers. The table has RLS with four policies that admit only an active staff user (dlv_is_staff()); there is no policy for customers or carriers and the table is not in the realtime publication, so a customer or carrier cannot read it even through the client libraries. The /admin pages call requireStaff. The only non staff path is the staff request email, which reads the number with the service role client inside notifyStaffOfRequest after the load exists and writes it only into that one email to staff. No customer or carrier query, page, email or export selects it.
- The key is pickup location + delivery location + truck size (UNIQUE). Direction matters (A to B and B to A are two lanes). 36 ft is allowed in the table and has no rows yet, as the owner said (upcoming projects).
- No snapshot: the number is read live from the load's CURRENT pickup, delivery and size on the load page, the board and the email. Editing a lane changes what an existing Requested load shows (reload). Nothing is copied onto the load.
- Both staff roles can add, edit, delete and import (staff_csr and staff_admin have identical operational rights, R4). Import only adds or updates, never deletes, and is all or nothing.
- The Moffett column of the owner's table is derived, not stored: pickup or delivery requires_moffett. The seven Y sites were set to requires_moffett = true in the data migration (SAMIH already was), so the derived value equals the owner's Y or N for all 25 rows (proved in rls.sql and in e2e). Side effect, intended: the booking form now locks the Moffett toggle on for those seven sites.
- Data migration 0016 joins the 17 location names BY NAME and refuses to write anything when one is missing or ambiguous. On a fresh database it does nothing (the migrations run before supabase/seed.sql, which has no locations yet) and supabase/seed.sql applies the same block after the locations exist. Production always has the locations, so 0016 does the work there. The five lanes the owner left out on purpose (125G, D Express and MTD to Etobicoke, 481 to Brampton, Mitrex to Winnipeg) were not invented.
- Re-applying 0016 (or seed.sql) sets the 25 seed scenarios back to the owner's numbers. That is deliberate for a re-run of a migration, but note it: if staff edit one of those 25 numbers and an operator later runs the seed file or the migration again by hand, the edit is overwritten. Rows staff added for other scenarios are never touched. The e2e suite re-applies seed.sql once (the idempotency test), which is why the lane tests never edit a seeded row.
- Number format: the same shape as an ITS load number (digits, optional dash and digits, at most 30).
- Notes are not sent in the email (only the number and the scenario text). They show on /admin/lanes.
- CSV export reuses the existing formula injection protection (a leading = + - @ tab or CR gets an apostrophe). Import removes that one apostrophe again so an exported file imports back unchanged. Import matches location names exactly, then case insensitively when that is unique.
- Apply: docs/APPLY-PACK-6.md (0015 and 0016), a separate owner supervised session; migration first, then the app. Deploying the app first is also safe (the card says the reference could not be loaded, the email says the lookup failed).
- Found by the a11y gate and fixed: the scrollable CSV preview table needed to be keyboard focusable (axe scrollable-region-focusable); it now has tabindex 0, a region role and a label.

## DLV-030 Rate requests (defaults, owner may change)
- A rate request is a separate object (table rate_requests, ref RQ-0001), not a load. It has no foreign key to or from loads and creates no load. "Book this lane" on a quoted request is a plain link to /book with no prefill (the locations on /book are chosen from the location list, the rate request holds free text cities).
- Cities and states are free text on purpose: the lane is not in the system, so there is no location row to pick. States are validated against the US states, DC and the Canadian provinces and territories (64 codes), in the server action and again as a CHECK in the database. Mexico is not accepted yet (see QUESTIONS).
- Limits: city 80 characters, dimensions 200, notes 1000, weight a whole number from 1 to 100000 lbs. Control characters are refused in cities and dimensions (they would break the email subject); notes may carry line breaks.
- Writes after the insert go only through two SECURITY DEFINER functions. There is no UPDATE or DELETE grant at all, so even an admin cannot edit a row by hand through the client libraries. The customer insert grant is column level (nine request columns) and a BEFORE INSERT trigger also forces requested_by = auth.uid(), status open and empty quote columns, so there are two layers.
- Re-quoting: staff may correct the rate of an already quoted request (set_rate_quote returns the previous status). Every field is replaced and quoted_by and quoted_at are restamped; the previous rate is not kept (no history table). A cancelled request cannot be quoted. A request cannot go back from quoted to open.
- Correction email: a correction sends the customer ONE message with the subject "Your rate was updated in the app (RQ-0001)" (the design only specified the first message). It also carries no amount. Reason: a customer who already saw the old rate in the app should be told it changed.
- The customer email never carries the amount, the currency or the quote notes (quote notes can contain prices). The rate lives in the app only.
- Cancelling: only the customer side, only while open, any active user of the same customer (not only the one who asked), by cancel_rate_request. A request of another customer reads as "not found" so its existence is not revealed. Staff cannot cancel (they simply do not quote it).
- Who is emailed on creation: every ACTIVE staff_admin, read with the service role after the row exists. Staff csr are not emailed (they see the open count and the list). Who is emailed on a rate: every ACTIVE customer user of the request's customer, not only the requester.
- Email failure is swallowed as in the load emails (the request or the rate is already saved). The staff screen says so: "Rate saved. The email to the customer could not be sent: tell them the rate is in the app."
- Rate limit: 30 requests per 10 minutes per customer user, counted from requested_by and created_at through the user client (the same shape as the load limit). The message names the limit.
- Validity: valid until is optional, a date, and cannot be in the past (Eastern date) when entered. An expired valid until does not change the status; the customer page just shows the date.
- Amounts: numeric(12,2), greater than 0 and below 100,000,000, at most two decimals typed. Currency CAD (default) or USD. The screens print "1,850.50 CAD".
- Not in the realtime publication: the Rates pages and the staff list refresh every 15 seconds (LiveRefresh polling, the same component as the board), which is enough for a flow that takes minutes. Adding the table to the publication later is one ALTER PUBLICATION and RLS would still apply.
- Board: the load board shows a link "Open rate requests" with the count of open requests (one head count query). The top menu item is "Rate requests" for staff and "Rates" for customers only; carriers have neither and the pages redirect them home.
- Found and fixed while testing: the prefilled amount on the correction form printed 1850.5 instead of 1850.50 (a JSON number); it is formatted with two decimals. The staff list overflowed at 375px with an 80 character city name (grid tracks without a minimum); fixed with explicit single column tracks and min-w-0.
- Apply: docs/APPLY-PACK-7.md (migration 0017 only), a separate owner supervised session. The migration is additive and touches no existing table; deploying the app first is safe except that the Rates pages and the board count show an error until the migration is applied, so apply first.

## DLV-032 Load photos (defaults, owner may change)
- Owner request (from carrier Kaja Transport, in real use since 2026-10-07): a photo is forced after the load is loaded and again at delivery, and the picture is taken inside the app, not chosen from the phone, with the time known automatically; Maria sees the photos on her side after the proper status change; the POD is taken in the app too.
- Status mapping, decided: no status was added. The pickup photo gates the step loading to enroute (button "Leave for delivery"); the delivery photo gates at_delivery to delivered (button "Mark delivered"). The owner's word "unloading" is the at_delivery status.
- The gate is a database rule, not a screen rule. set_load_status refuses a carrier role without the photo (message names the photo to take), so a stale page, a second device or a hand made call cannot skip it. The page also disables the button and shows the "Take loaded photo" / "Take delivery photo" step first.
- Staff are exempt so dispatch can fix a stuck load (a phone with a broken camera, a driver who forgot). The skip is not silent: the event note gets "Staff skipped the pickup photo (none on file)." or "Staff skipped the delivery photo (none on file)." after the staff note. The rule applies to any forward move into enroute or delivered by staff, including a jump over several steps.
- Time: the official time of a photo is load_documents.created_at, the server time of the insert, shown in Eastern time. The browser clock (captured_at) is stored in its own nullable column for reference only and is never shown, so a wrong phone clock cannot rewrite history.
- Who writes when: a carrier owner or driver of the load's own carrier writes a pickup photo only while the load is at_pickup or loading and a delivery photo only while it is at_delivery. The page offers the loaded step while loading (the at_pickup window exists so a photo taken a moment early is not refused) and the delivery step at_delivery.
- Who reads when: a customer reads a pickup photo once the load is enroute, at_delivery or delivered and a delivery photo once it is delivered, never of another customer's load; carriers read their own loads; staff read all. This is enforced on both the load_documents row and the storage object, and the signed link is created per page view and lives 5 minutes.
- Images only: the two photo kinds allow only jpg, jpeg, png and webp names in the path CHECK and in the access function; the storage insert policy also requires the object to be declared image/jpeg, image/png or image/webp, and a photo row can only be inserted when its image file already exists. So a PDF cannot sit under a photo name and an empty row cannot satisfy the gate. The app always uploads JPEG.
- Max 6 photos per kind per load, a BEFORE INSERT trigger with an advisory lock per load and kind (two parallel inserts cannot both pass). When the limit is reached the page hides the take button and says so; a photo can be removed to take another.
- Retake: a carrier removes its own photo while the step is open (delete_load_photo, a SECURITY DEFINER function that also returns the storage path; the server action removes the file with the service role). Nobody has a DELETE privilege on load_documents, so the existing rule "admin cannot DELETE load_documents directly" still holds. Removing the last photo locks the step again.
- Camera: getUserMedia with facingMode environment (ideal, so a laptop webcam works for testing), live preview, Take photo, Use this photo or Retake. The frame is drawn on a canvas, downscaled to at most 1600 px on the long side and encoded as JPEG quality 0.8 (about 100 to 400 kB). The stream is stopped as soon as the picture exists and on unmount. No dependency was added (MediaDevices and canvas only).
- Fallback: when the camera cannot be opened the dialog explains why in plain words (blocked, none found, used by another app) and offers the phone's camera app through input type=file accept=image/* capture=environment, plus "Try the camera again". The result goes through the same downscale and the same review step.
- POD: the in-app camera is the primary way (button "Take POD photo"); a small "Choose a file instead" link keeps the file area for a PDF the receiver handed over (PDF is now accepted as a POD file; it is stored as it is). The POD stays optional and is not a gate (owner ruling earlier). The file area no longer asks the phone for the camera (capture attribute removed), because it is the "I already have a file" path.
- Customer page: a Photos card on /loads/[id] lists what the database returned (kind label, Eastern time, thumbnail that opens full size). Before the status allows it the card says when the photos will appear. The page does not decide; it shows what the database returns.
- Staff: the Documents card of /admin/loads/[id] lists photos with their time and an Open link, lets staff upload a pickup or delivery photo on behalf of the carrier (png, jpg or webp, a file picker is fine for staff at a desk) and remove a photo. The status override form says that moving past a missing photo is allowed and recorded.
- Delete forever: delete_load_forever already returns EVERY storage_path of the load from load_documents, whatever the kind, so photo files are removed with the BOL and POD files. Two places knew the old path shape and were widened: the orphan log function (record_load_deletion_orphans) and the TypeScript DOC_PATH_RE in src/lib/admin/delete-load.ts (without it the server action would have counted photo paths as invalid and left the files behind). Both are tested with photos.
- Tests: helpers in e2e/support/helpers.ts seed a pickup photo for a load inserted as loading and a delivery photo for one inserted as at_delivery (opt out with photo: false), so the older specs keep testing what they test. Specs that give a POD as a file now open "Choose a file instead" first (helper podChooseFile).
- Playwright: the Chromium project launches with --use-fake-device-for-media-stream and --use-fake-ui-for-media-stream. The flags only matter when a page calls getUserMedia and only the camera specs grant the camera permission. WebKit has no fake camera: its camera specs are skipped and the fallback input path plus every gate run there.
- Apply: docs/APPLY-PACK-8.md (migration 0018 only), a separate owner supervised session. Apply 0018 first and deploy straight after: between the two, the old app has no photo step, so a carrier on the old app is refused at those two steps (staff can override). The pre-check reports how many production loads are in loading or at_delivery right now.
